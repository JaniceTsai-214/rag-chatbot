## 1. 單元測試規範

- 框架：`pytest` + `pytest-cov`。
- **完成的定義**：功能程式寫完，且 `pytest` 全部通過，才算完成。
- 覆蓋率目標：`src/rag_chatbot/` 核心模組 ≥ 80%（`app.py` 介面層不計）。
- **單元測試不依賴 Ollama**：使用 `tests/fakes.py` 的 `FakeEmbedder`（以關鍵字產生固定向量）與 `FakeLLM`（回傳可預期的文字）。
- 需要真實 Ollama 的測試標記 `@pytest.mark.ollama`，預設略過，用 `pytest -m ollama` 才執行。
- 資料庫使用暫存檔（`tmp_path`），測試之間互不影響。
- 單元測試用的小型 PDF/DOCX/MD/CSV 在測試執行時以程式產生（`tests/builders.py`），不放二進位檔進 Git。

### 各模組測試重點

| 模組 | 測試重點 |
|---|---|
| config / profiles | 讀取設定；情境變數代入；情境格式錯誤時有明確錯誤；可列出不存在的文件集；選填參數覆寫 |
| loaders | 各格式能擷取文字；PDF 頁碼正確；MD/DOCX 標題正確；DOCX 表格轉文字；FAQ 每列一筆；CSV UTF-8 與 Big5；空檔/壞檔有明確錯誤 |
| chunker | 長度上限、重疊、在句號/段落斷開、短文不切、不跨 Section |
| embedder | 前綴組合；批次切分（以假 Ollama client 測試） |
| llm | 呼叫參數（num_ctx、最多 tokens、temperature、keep_alive）；錯誤訊息（以假 Ollama client 測試） |
| db / vector_store | 建立資料表、版本檢查；新增/取代/刪除/清空；寫入失敗時舊資料不變；相似度排序正確；搜尋限定文件集；embedding 模型或維度不一致時拒絕 |
| ingest | 新檔匯入；相同 hash 跳過；修改後取代舊段落；向量化失敗時舊資料不變；刪除文件不刪原始檔 |
| cli | 各指令的輸出與錯誤訊息、結束碼、模型變更後 `--rebuild`（使用 FakeEmbedder） |
| keyword_index | 中英文斷詞（bigram）；BM25 排序；段落異動後重建 |
| retriever | 混合排名（RRF）；top_k；門檻依語意最高分判斷；參考資料長度上限與截斷；限定文件集 |
| smalltalk | 問候、道謝、身分詢問、套話字樣判斷；一般問題（含「你好，請問…」等長句）不誤判 |

| db | schema v1 → v2 自動升級 |
| history | 建立對話、寫入/讀取訊息（含類型、最高分）、重跑關聯；依情境列出對話；取最近幾輪問題 |
| rag | 正常回答帶 sources；低於門檻時回情境拒答文字且**不呼叫 LLM**；問候時回 greeting_text 且不檢索、不呼叫 LLM；Prompt 組裝（出處標示、變數代入）；多輪查詢組合；後處理（純拒答 → refused、刪除附加的拒答句）；寫入對話紀錄 |
| env | `.env` 解析（註解、引號、環境變數優先） |
| line | 簽章驗證；LINE API 請求格式與錯誤；訪客對話與閒置；引用標記移除；去重、群組忽略、非文字、頻率限制、佇列上限；reply／push 切換；Ollama 錯誤訊息；背景執行緒不因例外停止；webhook 簽章與 JSON 檢查（皆使用假 LINE API） |
| eval | 讀題集、計算命中預期來源、輸出報告 |

## 2. 功能測試方法

### 2.1 測試資料
`tests/functional/` 是一套獨立的測試環境（設定、情境、文件集、資料庫都與正式資料分開），文件內容為**虛構但具體**，含明確數字，方便判斷回答是否正確。

```
tests/functional/
├─ config.toml              # 指向下列路徑；資料庫為 tests/functional/app.db（不進 Git）
├─ make_testdata.py         # 產生下列測試文件
├─ profiles/                # intro（me + product）、me、product；subject = 王小明
└─ collections/
   ├─ me/
   │  ├─ 王小明履歷.docx
   │  └─ 作品集.md
   └─ product/
      ├─ 小算盤產品手冊.pdf
      └─ 小算盤FAQ.csv
```

| 檔案 | 內容（虛構） |
|---|---|
| `王小明履歷.docx` | 標題「工作經歷」「專長」各一節；工作經歷含「在小算盤團隊擔任後端工程師，負責雲端同步功能」 |
| `作品集.md` | `## 小算盤記帳 App`、`## 個人部落格` 兩節 |
| `小算盤產品手冊.pdf`（3 頁） | 第 1 頁：產品簡介；第 2 頁：方案價格（免費版、進階版每月 60 元）；第 3 頁：支援 iOS / Android、每日自動備份 |
| `小算盤FAQ.csv` | 5 筆問答（例如「可以多人共用帳本嗎？」→「進階版支援最多 5 人共用」） |

### 2.2 執行方式
1. 測試文件已在 Git 中；修改內容時才需重跑 `python tests/functional/make_testdata.py --force`（不加 `--force` 時不覆寫已存在的檔案，因為 DOCX 每次產生的 hash 都不同）。
2. 每個里程碑的功能測試都從乾淨狀態開始：刪除 `tests/functional/app.db`，再執行 `ingest`。
3. 一律指定測試設定：
   - M2、M3：`python -X utf8 -m rag_chatbot --config tests/functional/config.toml <指令>`
   - M5：`streamlit run app.py -- --config tests/functional/config.toml`
4. 依第 3 節逐項操作，將結果填入第 4 節「執行紀錄」：通過 / 不通過 / 備註（含回答時間）。
5. FT-03 會修改 `作品集.md`，測完以 `git checkout tests/functional/collections/me/作品集.md` 還原。

### 2.3 判定原則
- **正確**：回答內容與文件一致，且回答依據指向正確檔案/頁碼。
- **拒答正確**：文件中沒有的問題，回覆情境的拒答文字（含聯絡方式），不編造。
- **編造（嚴重缺陷）**：回答中出現文件沒有的事實，例如捏造價格、經歷。

### 4.3 M3 拒答規則比較（2026-10-25）

同一組參考資料、每種寫法各跑 2～3 次（qwen2.5:3b）：

| Prompt 規則 5 的寫法 | 可以接哪些 ERP？（有答案） | 智慧訂單多少錢？（無答案） | 她會不會 Rust？（無答案） |
|---|---|---|---|
| 「完全沒有答案時，只回答：『{拒答句}』；能回答時不要加上這句話」（原 v1） | ❌ 每次先抄拒答句再回答 → 後處理整段視為拒答 | ✅ 拒答 | — |
| 「能回答就直接回答，開頭不要說找不到資料；無法回答時只回覆：『{拒答句}』」 | ❌ 3/3 直接拒答 | ✅ 拒答 | — |
| 「找不到答案時，請回答：『{拒答句}』」 | ❌ 2/2 直接拒答 | ✅ 拒答（後半改寫） | ✅ 拒答 |
| 拿掉規則 5 | ✅ 正確 | ✅「尚未公開，建議聯繫」 | ✅「未提及」 |
| **「沒有提到的內容，請說明沒有提到，並建議來信 {contact}」（採用，D-028）** | ✅ 正確 | ✅ 1/2 多一句推測 | ✅ 未提及並附 Email |

結論：Prompt 中出現固定拒答句時，3B 傾向照抄。

**3B 模型已知的小瑕疵**（留待 M6 與 7B 比較）：偶有重複字（「蔡佳惠惠」「會會」）；把「資料沒提到」說成「不會」；稱呼規則用過頭（「她可以與 ERP 整合」，實為系統）；偶爾多一句推測（價格「預計依情境調整」）。
